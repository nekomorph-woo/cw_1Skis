## 1. Product Vision

### 1.1 Vision Statement

Kura (蔵) 是一个基于浏览器的本地优先微应用平台，让用户能够通过 AI 快速生成、运行和管理满足个人特定需求的小型应用。它填补了通用软件无法覆盖的长尾需求真空地带，实现"即时软件"（Just-in-Time Software）的理念——需要时生成，用完即走或留下迭代。

我们的愿景是让每个人都拥有自己的数字工具库，就像传统的日式仓库（蔵）一样，安全、私密、触手可及。

### 1.2 Value Proposition

| 维度 | 价值主张 |
|------|----------|
| **即时生成** | 通过 AI 在几分钟内生成满足特定需求的微应用，无需传统开发周期 |
| **数据主权** | 所有数据存储在本地文件系统，敏感数据无需上云，完全由用户控制 |
| **零依赖** | 无需 Node.js、无需 npm install、无需构建流程，代码极其干净 |
| **AI 友好** | 微应用只有 3 个文件，AI 只需理解极小的代码上下文，生成质量高 |
| **模块化** | @shared 模块系统实现公共代码复用，避免重复造轮子 |
| **标准化** | 固定的目录结构和技术栈，降低 AI 生成错误率 |

## 2. Problem Statement

### 2.1 Current State

目前的软件生态存在以下问题：

1. **通用软件覆盖不足**：市面上的软件 (Excel, Notion, Photoshop) 都是为了满足 80% 的通用需求设计的，剩下 20% 的个性化需求无法被覆盖
2. **传统开发门槛高**：开发一个简单的小工具需要配置 Node.js、Webpack、React 全家桶，环境配置复杂、学习曲线陡峭
3. **数据隐私风险**：云端 SaaS 服务需要上传数据，敏感数据 (财务、客户名单、代码库) 不敢上云
4. **AI 生成代码的上下文问题**：在复杂项目中 AI 容易产生"精神分裂"，混淆前后端边界

### 2.2 Pain Points

- **[P1] 长尾需求无法满足**
  - 用户有特定格式日志文件转换、专用库存计算器等个性化需求
  - 通用软件无法满足，定制开发成本过高

- **[P2] 开发门槛过高**
  - 想要实现简单功能需要配置复杂的开发环境
  - 非技术人员无法快速实现自己的小想法

- **[P3] 数据隐私担忧**
  - 不敢将敏感数据上传到云端 SaaS 服务
  - 缺乏既安全又便利的本地工具

- **[P4] AI 生成代码不准确**
  - AI 在复杂项目中容易混淆前后端边界
  - 生成不符合架构的代码，需要大量人工修正

- **[P5] 修改需求语义歧义**
  - 用户说"把按钮改红"，AI 不知道指哪个按钮
  - 上下文不准确导致生成错误

### 2.3 Impact

如果不解决这些问题：
- 用户只能忍受通用软件的不匹配，或花费高昂成本定制开发
- 许多有价值的想法因为无法快速实现而被放弃
- 敏感数据无法利用现代 SaaS 的便利性
- AI 辅助编程的优势无法充分发挥

## 3. User Personas

### 3.1 Primary Users

| Persona | 描述 | 目标 | 痛点 |
|---------|-------------|-------|-------------|
| **效率工具爱好者** | 追求工作效率的知识工作者，经常有各种小需求 | 快速实现工作流中的小工具，提高效率 | 不懂编程，无法自己实现 |
| **独立开发者** | 需要快速构建原型的开发者 | 快速验证想法，不需要配置复杂环境 | 厌倦了配置 webpack、vite 等构建工具 |
| **隐私敏感用户** | 注重数据安全的企业或个人 | 在保护隐私的前提下享受 AI 辅助编程 | 不敢将代码上传到云端 IDE |
| **极客与创客** | 喜欢尝试新技术的技术爱好者 | 探索 AI + 本地应用的新可能性 | 缺乏一个统一的平台来管理各种小工具 |

## 4. User Stories

### 4.1 Core Features

- **[US-001]:** 作为一个效率工具爱好者，我想要通过自然语言描述快速生成一个计算器应用，这样我就能立即使用它来处理日常工作
- **[US-002]:** 作为一个隐私敏感用户，我想要所有数据都存储在本地，这样我的敏感财务信息就不会上传到云端
- **[US-003]:** 作为一个独立开发者，我想要在一个统一的界面中管理多个微应用，这样我就能快速切换使用不同工具
- **[US-004]:** 作为一个非技术用户，我想要通过点击界面元素来指定修改位置，这样 AI 就能准确理解我的需求

### 4.2 Secondary Features

- **[US-101]:** 作为一个团队协作者，我想要通过 Git 同步我的应用，这样团队成员也能使用我创建的工具
- **[US-102]:** 作为一个高级用户，我想要创建可复用的公共模块，这样我就能在不同应用间共享代码
- **[US-103]:** 作为一个内容创作者，我想要将应用打包成独立 EXE 分享给朋友，这样他们不需要安装任何环境就能使用

| FR-005 | 系统必须提供 Import Maps 支持 @shared 模块引用 | P0 |

## 6. Non-Functional Requirements

### 6.1 Performance

| Metric | Target | Measurement |
|--------|--------|-------------|
| 应用加载时间 | < 2 秒 | 从点击到应用完全渲染 |
| 标签切换时间 | < 100ms | 从点击到标签内容显示 |
| AI 生成响应 | < 10 秒 | 从提交需求到代码生成 |
| 内存占用 (单个应用) | < 50MB | 单个 iframe 内存占用 |

### 6.2 Security

- 前端 JS 运行在浏览器沙箱中，不能直接读写本地文件
- 所有文件操作必须通过 Bun 后端 API 进行
- 用户数据存储在本地，不上传到任何云端服务
- AI API Key 由用户本地配置，不经过第三方服务器

### 6.3 Scalability

- 支持同时打开至少 10 个微应用而不影响性能
- 支持工作区包含至少 100 个微应用
- 支持至少 50 个 @shared 公共模块

### 6.4 Compatibility

| Platform | Versions | Requirements |
|----------|----------|--------------|
| Windows | 10/11 | WebView2 (系统自带) |
| macOS | 11+ | Safari 16.4+ 或 Chrome 89+ |
| Linux | Ubuntu 20.04+ | Chrome 89+ |

### 6.5 Maintainability

- 微应用采用标准化的三文件结构 (index.html + logic.js + style.css)
- 代码使用 JSDoc 注释提供类型提示
- 遵循 ESLint 规范进行代码风格检查
- 提供完整的平台文档供 AI 参考

## 7. User Interface Requirements

### 7.1 Design Principles

- **简洁优先**：界面最小化，突出应用内容
- **标准化**：所有微应用使用统一的 UI 组件库 (DaisyUI)
- **响应式**：支持不同屏幕尺寸
- **原生感**：尽可能接近原生应用的体验

### 7.2 Key Screens

| Screen | 描述 | 关键元素 |
|--------|-------------|--------------|
| **启动界面** | 双击 EXE 后的首屏 | 加载动画、版本信息 |
| **主界面** | 多标签页容器 | 顶部标签栏、菜单按钮、工作区 |
| **AI 面板** | AI 对话和代码生成区域 | 对话历史、输入框、生成按钮 |
| **应用列表** | 显示所有可用应用 | 应用卡片、图标、名称、描述 |

### 7.3 Accessibility

- 支持键盘导航 (Tab 切换、快捷键)
- 支持屏幕阅读器
- 提供足够的颜色对比度
- 支持字体大小调整

## 8. Data & Privacy

### 8.1 Data Collection

| 数据类型 | 用途 | 保留期 |
|-----------|---------|-----------|
| 用户生成的应用代码 | 本地运行 | 永久 (由用户控制) |
| AI 对话历史 | 改进体验 | 可选，由用户控制 |
| 工作区配置 | 记住用户设置 | 永久 |
| 错误日志 | 问题诊断 | 可选，由用户控制 |

### 8.2 Privacy Requirements

- 所有用户数据默认存储在本地
- 不向任何第三方服务器发送用户代码 (除用户配置的 AI API)
- AI API Key 由用户本地管理，不经过平台服务器
- 提供数据导出功能，方便用户备份

## 10. Assumptions & Constraints

### 10.1 Assumptions

- 用户使用的浏览器支持 Import Maps (Chrome 89+, Safari 16.4+)
- 用户有稳定的网络连接以访问 AI API
- 用户愿意安装本地程序 (EXE) 来获得更好的体验
- AI 模型的代码生成能力会持续提升

### 10.2 Constraints

- 必须使用浏览器沙箱运行前端代码
- 文件操作必须通过后端进行
- 受限于 AI 模型的上下文窗口大小
- 受限于浏览器的内存和性能限制

## 11. Risks & Mitigation

| 风险 | 影响 | 概率 | 缓解措施 |
|------|--------|-------------|------------|
| AI 生成代码质量不稳定 | 高 | 中 | 提供强约束 DSL 和代码模板 |
| 用户浏览器不支持新特性 | 高 | 低 | 提供浏览器兼容性检测和降级方案 |
| 微应用间存在冲突 | 中 | 中 | 使用 iframe 进行严格隔离 |
| 打开过多标签导致内存溢出 | 中 | 中 | 实现自动销毁最久未使用标签的策略 |
| AI API 成本过高 | 中 | 低 | 支持用户自备 API Key |
