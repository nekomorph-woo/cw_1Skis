**Document Version:** 1.0

**Project Name:** Kura (蔵) - 本地化微应用生成与运行平台

## Executive Summary

当前软件生态存在一个显著的空白：通用软件无法满足用户的个性化长尾需求，而传统开发方式门槛过高、周期过长。Kura 项目旨在通过 AI 辅助和本地优先架构，让用户能够快速创建满足个人特定需求的小型应用，同时保护数据隐私和安全。

---

## Problem Statement

### What is the problem?

软件开发，特别是满足个人特定需求的小工具开发，存在"高成本、低效率"的问题。用户想要实现一个小功能（如特定格式转换、专用计算器），却需要配置复杂的开发环境、学习多种技术栈。同时，云端 SaaS 服务需要上传数据，存在隐私风险。

### Who is affected?

| 利益相关者 | 影响 | 严重程度 |
|-------------|--------|----------|
| 效率工具爱好者 | 无法快速实现工作流中的小工具，影响效率 | 高 |
| 独立开发者 | 厌倦了配置复杂的构建环境，只想快速验证想法 | 中 |
| 隐私敏感用户 | 不敢将敏感数据上传到云端，无法享受现代 SaaS 的便利 | 高 |
| 非技术用户 | 有想法但无法自己实现，只能等待或放弃 | 中 |

### When does it occur?

这个问题在以下场景中尤为突出：
- 用户需要处理特定格式的数据（如日志文件转换）
- 用户需要一个专用的小工具（如库存计算器）
- 用户想要快速验证一个想法
- 用户需要处理敏感数据，不敢使用云端服务

## Current State

### How things work today

当前用户有以下几种选择：

1. **使用通用软件**：Excel、Notion 等，但无法满足个性化需求
2. **云端 SaaS 服务**：功能强大，但需要上传数据，存在隐私风险
3. **传统开发**：配置 Node.js、Webpack、React 全家桶，门槛过高
4. **放弃需求**：因为无法实现而放弃

### Current limitations

```
当前工作流：
[产生需求] → [选择方案] → [配置环境] → [学习技术] → [开发测试] → [部署使用]
              ↓            ↓            ↓            ↓
            [通用软件不匹配]  [配置复杂耗时]  [学习曲线陡峭]  [周期过长]
```

**关键限制：**
- 环境配置复杂（Node.js、npm、webpack 等）
- 学习曲线陡峭（前端、后端、构建工具）
- 开发周期长（从想法到可用需要数天）
- 数据隐私问题（云端服务需要上传）

### User stories illustrating the problem

> **效率工具爱好者:** "我需要一个将特定格式日志文件转换为图表的工具，Excel 做不到，找人开发成本太高，自己又不会编程，只能手动处理每天花 2 小时。"

> **独立开发者:** "我有一个简单的想法，想快速验证。但是配置 Node.js、安装依赖、配置 Webpack 就花了半天时间，还没开始写代码。"

> **隐私敏感用户:** "我想用一个任务管理工具，但是不敢把公司数据上传到 Notion 或 Trello。有没有本地版的？"

## Impact Analysis

### Business Impact

| 影响领域 | 当前影响 | 如不解决的潜在后果 |
|----------|----------|---------------------|
| 个人生产力 | 大量时间浪费在重复性手动操作上 | 无法提高工作效率，竞争优势丧失 |
| 创新能力 | 许多小想法因为无法实现而被放弃 | 创新受阻，错失机会 |
| 数据安全 | 要么放弃使用云端工具，要么承担隐私风险 | 数据泄露风险增加 |
| 开发效率 | 非技术人员无法实现自己的工具想法 | 依赖他人，响应速度慢 |

### User Impact

- **效率低下**: 每天花费大量时间在可以用自动化解决的任务上
- **想法无法实现**: 许多有价值的小想法因为无法快速实现而被放弃
- **隐私担忧**: 不敢使用云端服务，只能忍受低效的本地工具
- **学习成本高**: 想要学习编程，但被复杂的环境配置劝退

### Operational Impact

- **资源浪费**: 重复性工作占用大量人力资源
- **技术债务**: 为了快速实现，常常使用不规范的临时方案
- **维护困难**: 缺乏统一的管理平台，工具分散难以维护

## Root Cause Analysis

### Underlying causes

| 原因 | 证据 | 贡献度 |
|------|------|--------------|
| 传统开发环境复杂 | Node.js 生态需要学习多种工具 | 高 |
| 通用软件无法覆盖所有场景 | 长尾需求分散，难以一一满足 | 高 |
| 云端服务模式限制 | 商业模式决定了需要集中数据 | 中 |
| 缺乏统一的小工具管理平台 | 现有工具要么太重 (IDE) 要么太轻 (单独的 HTML 文件) | 中 |

### Why hasn't this been solved before?

- **技术限制**: 以前浏览器能力有限，无法直接操作本地文件
- **AI 能力不足**: 以前的 AI 代码生成质量不够高
- **市场需求被忽视**: 长尾需求分散，商业价值不明显
- **用户习惯**: 用户习惯了使用通用软件或忍受低效

## Success Criteria

### What does success look like?

| 标准 | 度量方式 | 目标 |
|------|----------|------|
| 应用生成成功率 | 成功生成可运行应用的比例 | > 80% |
| 应用生成时间 | 从需求到可用的时间 | < 5 分钟 |
| 用户满意度 | NPS 评分 | > 50 |
| 隐私保护 | 数据本地存储比例 | 100% |

### Definition of done

- [ ] 用户可以通过自然语言生成可运行的微应用
- [ ] 生成的应用可以立即使用
- [ ] 所有数据存储在本地
- [ ] 提供多标签页管理界面
- [ ] 支持 Git 同步和备份
- [ ] 文档完整，用户可以自助使用

## Constraints & Considerations

### What boundaries exist?

- **浏览器能力限制**: 前端代码运行在沙箱中，不能直接读写文件
- **AI 能力限制**: AI 的代码生成质量依赖于模型能力
- **用户技术门槛**: 目标用户可能完全没有编程经验
- **平台兼容性**: 需要支持 Windows、macOS、Linux

### What must be preserved?

- **数据隐私**: 所有用户数据必须存储在本地
- **简单易用**: 不能引入复杂的配置流程
- **开放性**: 用户应该能够完全控制自己的代码和数据

### What are the risks of inaction?

- **用户持续低效**: 无法解决实际问题
- **市场机会丧失**: 其他类似产品可能抢先占领市场
- **技术债务累积**: 继续使用不规范的各种临时方案

## Context & Background

### Relevant history

- **Web 技术演进**: 现代浏览器 (Chrome/Edge) 支持 File System Access API，可以直接操作本地文件
- **AI 技术突破**: GPT-4、Claude 等大模型的代码生成能力显著提升
- **本地优先趋势**: 数据隐私意识增强，本地工具需求增长

### Previous attempts

| 尝试 | 结果 | 经验教训 |
|------|---------|-----------------|
| Electron 应用 | 体积大、资源占用高 | 需要更轻量的方案 |
| 纯 Web 应用 | 功能受限，无法访问本地文件 | 需要后端支持 |
| No-Code 平台 | 依赖云端，数据隐私问题 | 需要本地优先 |

### Assumptions

- 用户有稳定的网络连接以访问 AI API
- 用户使用的浏览器支持现代 Web 标准 (Import Maps 等)
- 用户愿意安装本地程序以获得更好的体验

## Related Problems

### Connected issues

- **长尾需求聚合**: 如何发现和共享用户创建的微应用？
- **模块复用**: 如何避免在不同应用中重复编写相同功能？
- **跨平台一致性**: Windows、macOS、Linux 上的体验如何保持一致？

### Dependencies

- **浏览器 API 支持**: 依赖现代浏览器的 File System Access API
- **AI 模型可用性**: 依赖第三方 AI API 的稳定性
- **Git 生态**: 依赖 Git 作为版本控制和同步机制
